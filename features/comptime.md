# Comptime — Compile-Time Execution

Compile-time evaluation via an AST interpreter in the self-hosted compiler (wc). Not implemented in w0.

## Design Philosophy

Comptime lets ordinary Whist code run during compilation to introspect types and generate code. There is no separate macro language, no plugin API, no external tooling — comptime functions are Whist functions that happen to execute at compile time. The compiler's AST, type system, and symbol tables are exposed through a set of compiler builtins.

This is the general-purpose mechanism that subsumes the need for user-defined source generators, proc macros, or template metaprogramming. The built-in derives from [Reflection Phase 1](reflection.md) handle the common cases in both w0 and wc; comptime handles everything else in wc.

## Why wc Only

The w0 bootstrap compiler is written in C. Implementing a Whist interpreter in C means writing the language semantics twice (once for the C codegen, once for the C interpreter) and keeping them in sync — the single hardest maintenance burden in languages with comptime (see Zig).

The self-hosted compiler (wc) is written in Whist. The comptime interpreter is Whist interpreting Whist — same AST representation, same type system, same semantic rules. Adding a language feature to wc automatically makes it available at comptime. No dual maintenance.

### Bootstrapping

```
w0 (C, no comptime) ──compiles──→ wc v1 (Whist, implements comptime, doesn't use it)
wc v1                ──compiles──→ wc v2 (can use comptime in its own source)
wc v2                ──compiles──→ wc v3 (etc.)
```

This is standard compiler bootstrapping. wc v1 must be compilable by w0, so it cannot use comptime in its own source. Once wc can compile itself, later versions are free to use comptime internally.

## Syntax

### Comptime Functions

Functions marked `comptime` are evaluated by the compiler, not emitted into the output:

```whist
comptime func field_count(comptime T: type) -> i64 {
    var info = @type_info(T);
    return info.field_count;
}
```

### Comptime Parameters

Parameters marked `comptime` must be known at compile time. The compiler evaluates the function for each unique set of comptime arguments (similar to monomorphization):

```whist
comptime func has_field(comptime T: type, comptime name: string) -> bool {
    var info = @type_info(T);
    foreach i in 0..info.field_count {
        if info.fields[i].name == name {
            return true;
        }
    }
    return false;
}
```

### Comptime Blocks

Inline comptime evaluation within a runtime function:

```whist
func process<T>(value: T) -> string {
    comptime {
        if !has_field(T, "name") {
            @compile_error("process() requires a type with a 'name' field");
        }
    }
    return value.name;
}
```

### Comptime Source Emission

Comptime functions that return `string` can be used with `@emit` to inject generated source into the compilation:

```whist
@[derive(Debug)]  // Phase 1: built-in, works in w0 and wc
struct Point { x: i64, y: i64 }

@emit(generate_to_json(Point))  // Phase 3: comptime, wc only

func main() -> i32 {
    var p = Point { x: 1, y: 2 };
    std.print(Point_to_json(&p));  // generated by comptime
    return 0;
}
```

## Compiler Builtins

Builtins are prefixed with `@` and are only available in comptime context. They provide read-only access to the compiler's internal state.

### Type Introspection

```whist
// Get full type information for a type
@type_info(T) -> TypeInfo

// Get fields of a struct type
@fields(T) -> Span<FieldInfo>

// Get enum variants
@variants(T) -> Span<EnumValueInfo>

// Get methods on a type
@methods(T) -> Span<MethodInfo>

// Get the name of a type as a string
@type_name(T) -> string

// Check if a type has a specific attribute
@has_attribute(T, "attr_name") -> bool

// Get attribute arguments
@get_attribute(T, "attr_name") -> ?AttributeInfo
```

### Compile-Time Diagnostics

```whist
// Emit a compile error with a custom message
@compile_error("message")

// Emit a compile warning
@compile_warning("message")
```

### Source Generation

```whist
// Inject a string as Whist source code into the compilation
@emit(source_string)
```

## AST Interpreter

### Architecture

The comptime interpreter is a tree-walking evaluator embedded in the wc compiler. It operates on the same AST nodes that the checker produces and the codegen consumes:

```
                     wc compilation pipeline
                     ═══════════════════════

lexer → parser → checker → [comptime interpreter] → codegen
                               │
                               ├── evaluate comptime functions
                               ├── execute comptime blocks
                               ├── process @emit directives
                               ├── parse emitted source
                               └── merge into AST → re-check
```

### Interpreter State

The interpreter maintains its own execution state, separate from the runtime:

```whist
struct ComptimeInterpreter {
    // The compiler's checked AST and type tables (read-only)
    ast: *Node,
    checker: *Checker,

    // Interpreter's own state
    call_stack: Vec<ComptimeFrame>,
    values: Vec<ComptimeValue>,

    // Accumulated source output from @emit
    emitted_source: string,

    // Recursion / step limits
    max_depth: i32,
    max_steps: i64,
    current_steps: i64,
}

struct ComptimeFrame {
    func_name: string,
    locals: HashMap<string, ComptimeValue>,
    return_value: ?ComptimeValue,
}
```

### Comptime Values

The interpreter works with a tagged value type that can represent any Whist value:

```whist
enum ComptimeValueKind {
    Void,
    Bool,
    Int,
    Float,
    Char,
    String,
    Struct,
    Enum,
    Array,
    Span,
    Tuple,
    Type,       // first-class type values (only at comptime)
    Null,
}

struct ComptimeValue {
    kind: ComptimeValueKind,
    // ... payload per kind
}
```

The key distinction from runtime values: `Type` is a first-class value at comptime. You can pass types as arguments, store them in variables, and introspect them. This is what makes `comptime T: type` work.

### What the Interpreter Supports

The interpreter must evaluate a subset of Whist sufficient for type introspection and string construction:

| Feature | Supported | Notes |
|---|---|---|
| Arithmetic (`+`, `-`, `*`, `/`, `%`) | Yes | Integer and float |
| Comparison (`==`, `!=`, `<`, `>`, `<=`, `>=`) | Yes | |
| Logical (`&&`, `\|\|`, `!`) | Yes | |
| String concatenation (`+`) | Yes | Core use case |
| Variables (`var`, `const`) | Yes | Local to comptime scope |
| Control flow (`if`, `while`, `for`, `foreach`) | Yes | |
| Function calls | Yes | Comptime functions only |
| Struct construction | Yes | For building return values |
| Array/span indexing | Yes | For iterating type info |
| Member access (`.`) | Yes | For accessing TypeInfo fields |
| Pointer operations | No | No heap at comptime |
| I/O (print, file, network) | No | Pure computation only |
| Allocation (new, malloc) | No | Stack-only at comptime |
| Extern/FFI calls | No | No C interop at comptime |
| Closures | No (initially) | Can be added later |
| Recursion | Yes | With depth limit |

### Execution Limits

To prevent infinite loops and excessive compilation times:

```whist
// Default limits (configurable via compiler flags)
const COMPTIME_MAX_DEPTH = 64;       // max call stack depth
const COMPTIME_MAX_STEPS = 1000000;  // max interpreter steps
const COMPTIME_MAX_OUTPUT = 1048576; // max emitted source bytes (1MB)
```

Exceeding a limit produces a compile error:

```
error: comptime execution exceeded step limit (1000000 steps)
  --> generators.w:15:5
   |
15 |     comptime { generate_all(T); }
   |               ^^^^^^^^^^^^^^^^
   = help: increase limit with --comptime-max-steps=N
```

## Execution Model

### Evaluation Order

1. The checker completes its pass (all types resolved, symbols defined)
2. The comptime interpreter runs all `comptime` blocks and `@emit` directives in source order
3. Emitted source is collected, parsed, and type-checked
4. The merged AST is passed to codegen

### No Cascading

Emitted source cannot itself contain comptime blocks. This is a deliberate restriction that prevents:
- Infinite generation loops
- Order-dependent generation
- Unpredictable compilation times

If cascading is needed in the future, it can be added with a fixed depth limit.

### Determinism

Comptime evaluation is deterministic — no I/O, no randomness, no time-dependent operations. Same source always produces same output. This enables:
- Reproducible builds
- Caching of comptime results
- Parallel comptime evaluation (future optimization)

### Isolation

Comptime functions cannot:
- Read or write files
- Make network requests
- Call extern/FFI functions
- Access environment variables
- Allocate heap memory

They can only:
- Compute with values
- Introspect types via builtins
- Build strings
- Return values or emit source

## Grammar Changes

```bnf
comptime_func  = "comptime" func_decl

comptime_block = "comptime" block
emit_directive = "@emit" "(" expression ")"
```

## Integration with Reflection

| Feature | w0 | wc | Mechanism |
|---|---|---|---|
| `@[derive(Debug, Eq, ...)]` | Yes | Yes | Built-in compiler logic |
| `@[reflect]` / `@type_info(T)` | Yes | Yes | Static descriptor tables |
| Custom comptime generators | No | Yes | AST interpreter |
| `@emit(...)` source injection | No | Yes | AST interpreter |
| `comptime` blocks | No | Yes | AST interpreter |

Programs that only use Phase 1 and Phase 2 features compile with both w0 and wc. Programs that use comptime require wc.

## Implementation Considerations

### Building the Interpreter Incrementally

The interpreter doesn't need to support all of Whist on day one. A practical implementation order:

1. **Literal evaluation** — integers, strings, bools
2. **Arithmetic and comparison** — binary/unary operations
3. **Variables and assignment** — local comptime state
4. **Control flow** — if/while/for
5. **Function calls** — comptime-to-comptime calls
6. **`@type_info` builtin** — bridge to compiler's type tables
7. **Struct field access** — `info.fields[i].name`
8. **`@emit` directive** — parse emitted source and merge
9. **String operations** — concatenation, conversion builtins

Steps 1-5 give you a working interpreter. Steps 6-8 connect it to the compiler. Step 9 makes it useful for code generation.

### Sharing AST with the Compiler

The interpreter reads the same `Node` and `Type` structures the compiler uses. It doesn't need its own AST representation. The `@type_info` builtin is a thin wrapper that converts the compiler's `Type*` into a `ComptimeValue` of kind `Struct` (a `TypeInfo`).

### Testing Strategy

Comptime can be tested independently of the full wc compiler:

1. **Unit tests** — test the interpreter against simple expressions and control flow
2. **Integration tests** — test `@type_info` against known struct definitions
3. **End-to-end tests** — test `@emit` producing correct source that compiles
4. **Limit tests** — verify step/depth limits trigger correctly
5. **Error tests** — verify good diagnostics for unsupported operations at comptime

### Error Reporting

Comptime errors should show both the comptime call site and the interpreter stack:

```
error: comptime evaluation failed
  --> main.w:10:1
   |
10 | @emit(generate_serialize(User))
   |       ^^^^^^^^^^^^^^^^^^^^^^^^
   |
  in comptime function generate_serialize(User)
  --> generators.w:25:12
   |
25 |     var x = info.fields[i].nonexistent;
   |             ^^^^^^^^^^^^^^^^^^^^^^^^^^ FieldInfo has no member 'nonexistent'
```

## Open Questions

1. **Comptime return types**: Should comptime functions be limited to returning `string` (for `@emit`) and primitive types? Or allow returning arbitrary structs?
2. **Comptime-visible attributes**: Should comptime be able to see *all* attributes, or only explicitly comptime-visible ones?
3. **Standard comptime library**: Should there be a `comptime.` standard library module with helpers for code generation (string builders, indentation utilities, etc.)?
4. **Incremental comptime**: When a source file changes, can we cache comptime results for unchanged types?
5. **Comptime in tests**: Should test files be able to use comptime even when compiled with w0? (Would require w0 to shell out to wc for comptime blocks.)
6. **`comptime var`**: Should there be comptime variables at module scope that persist across comptime evaluations? Useful for collecting information across multiple `@emit` calls.
7. **Inline emission vs string emission**: Is returning a string and parsing it the right model? Alternatively, comptime could construct AST nodes directly (more complex but avoids string→parse round-trip).

## Examples

### Custom Serialization

```whist
comptime func generate_to_json(comptime T: type) -> string {
    var info = @type_info(T);
    var out = "func " + info.name + "_to_json(self: *" + info.name + ") -> string {\n";
    out += "    var result = \"{\";\n";
    foreach i in 0..info.field_count {
        var f = info.fields[i];
        if i > 0 { out += "    result += \", \";\n"; }
        out += "    result += \"\\\"" + f.name + "\\\": \";\n";
        if f.type_name == "string" {
            out += "    result += \"\\\"\" + self->" + f.name + " + \"\\\"\";\n";
        } else if f.type_name == "i64" {
            out += "    result += i64_to_string(self->" + f.name + ");\n";
        } else if f.type_name == "bool" {
            out += "    result += bool_to_string(self->" + f.name + ");\n";
        } else {
            @compile_error("generate_to_json: unsupported field type '" + f.type_name + "'");
        }
    }
    out += "    result += \"}\";\n";
    out += "    return result;\n";
    out += "}\n";
    return out;
}

@emit(generate_to_json(User))
```

### Compile-Time Validation

```whist
comptime func assert_has_id(comptime T: type) -> void {
    var info = @type_info(T);
    var found = false;
    foreach i in 0..info.field_count {
        if info.fields[i].name == "id" {
            found = true;
        }
    }
    if !found {
        @compile_error(info.name + " must have an 'id' field to be used as a database entity");
    }
}

@[entity]
struct User {
    id: i64,
    name: string,
}

comptime { assert_has_id(User); }  // OK

@[entity]
struct Config {
    key: string,
    value: string,
}

comptime { assert_has_id(Config); }  // compile error: Config must have an 'id' field
```

### Enum String Tables

```whist
comptime func generate_enum_strings(comptime T: type) -> string {
    var info = @type_info(T);
    var out = "func " + info.name + "_to_string(value: " + info.name + ") -> string {\n";
    out += "    if value == ";
    foreach i in 0..info.enum_value_count {
        var v = info.enum_values[i];
        if i > 0 { out += " else if value == "; }
        out += info.name + "::" + v.name + " { return \"" + v.name + "\"; }\n";
    }
    out += "    return \"unknown\";\n";
    out += "}\n";
    return out;
}

enum Color { Red, Green, Blue }
@emit(generate_enum_strings(Color))

func main() -> i32 {
    std.print(Color_to_string(Color::Red));  // "Red"
    return 0;
}
```

### Generic Comptime Functions

```whist
// Works with any struct type that has @[reflect]
comptime func generate_print_fields(comptime T: type) -> string {
    var info = @type_info(T);
    var out = "func " + info.name + "_print_fields(self: *" + info.name + ") -> void {\n";
    foreach i in 0..info.field_count {
        var f = info.fields[i];
        out += "    std.print(\"" + f.name + ": \");\n";
        out += "    std.print(to_string(self->" + f.name + "));\n";
        out += "    std.print(\"\\n\");\n";
    }
    out += "}\n";
    return out;
}

@[reflect]
struct Point { x: i64, y: i64 }

@[reflect]
struct User { name: string, age: i64 }

@emit(generate_print_fields(Point))
@emit(generate_print_fields(User))
```
